# ainsで人とAIの役割を分ける

ains は、目的・制約・受入条件を人と揃え、その範囲の実装と修正をAIに任せるワークフローです。人は仕様、計画、差分、展開を判断します。入口の `ains` から、その変更に必要な工程を使えます。

## 最初に覚えるコマンドは1つ

Claude Codeは `/ains`、Codexは `$ains` です。コマンドだけなら状態を確認し、対象を指定して作業を依頼すれば、その変更の工程を進めます。

```text
初回設定 → 仕様 → 計画 → テスト先行の実装 → レビュー・出荷判断
             ↑人の承認  ↑人の承認                  ↑人の判断
```

一連の作業を依頼した場合は、同じ範囲の承認後に次へ進みます。個別工程だけを依頼した場合は、その工程で終わります。承認済みのファイルがあるだけで別の作業を始めることはありません。

## 何を任せ、何を判断するか

| 人が判断すること | AIが調べ、実行すること |
|---|---|
| 目的・制約・受入条件・対象外 | 既存実装や契約の調査、仕様案 |
| 方針・任せる範囲・停止条件 | タスク案、完了条件、検査方法 |
| 差分の妥当性・マージ・展開 | テスト先行の実装、検査、独立レビュー、出荷資料 |

不明な事実はAIが調べ、未決の判断には推奨案を添えて質問します。平文で聞くときは1回に1判断とし、回答を待ちます。既に答えた同じ範囲の判断は聞き直しません。仕様変更では仕様・計画の承認を見直します。

操作の許可は別に扱います。編集・ローカル検査・コミット・push・PR・マージ・デプロイは、利用者が任せた範囲に従います。スキルの起動や工程の続行によって、許可が増えることはありません。

## 変更の記録を少なく保つ

通常は `docs/changes/<日付-slug>/` に2ファイルを置きます。

| ファイル | 残す内容 |
|---|---|
| spec.md | 目的、文脈、制約、受入条件、対象外、観測された契約、未決事項 |
| tasks.md | 実装方針、任せる範囲、停止条件、Done when付きのタスク、メモ |

承認状態は各ファイルの `status: draft | approved` に記録します。小さな変更はタスクをspecへまとめ、tasksを省きます。1行の修正やタイポは一連の工程に乗せず、必要な修正と検査を行えます。

検証結果はPR本文へまとめます。PRを作らない場合は `pr.md` に本文の下書きを置きます。出荷の判断は `ains-ship` で求めます。振り返りは出荷後に明示して依頼します。

## スキルの使い分け

16スキルは全て一括導入し、必要な工程を使います。兄弟スキルの参照に依存するため、個別導入は動作保証の対象外です。

| 呼び方 | 対象と役割 |
|---|---|
| 利用者が明示して始める | `ains`：状態確認と一連の作業の入口 |
| 個別にも、一連の依頼の中でも使う | `ains-setup`・`ains-spec`・`ains-tasks`・`ains-build`・`ains-ship`：設定から出荷準備まで |
| 利用者が必要なときに依頼する | `ains-retro`・`ains-team-canvas`・`ains-harness`・`ains-tool-access`：振り返り、チーム合意、CI整備、外部ツール接続 |
| AIが必要に応じて使う | `ains-grilling`・`ains-tdd`・`ains-review`・`ains-review-gate`・`ains-release-safety`・`ains-context-care`：質問、実装、レビュー、確認規則、展開、文脈管理 |

明示起動限定の設定は、製品のネイティブなスキル起動に対するものです。依頼と権限の範囲で手順・テンプレート・スクリプトを通常参照できます。ファイルアクセスを遮断する仕組みや、Codexの文脈節約量を保証するものではありません。

## 設定はプロジェクトで共有する

`ains-setup` が検査コマンド、変更の置き場所、人の確認規則、操作権限、相談先を記録します。正本は `AGENTS.md` のAgent skills節で、Claude Codeは `CLAUDE.md` の `@AGENTS.md` から読みます。

既存の値と無関係な文章は保持します。同じ設定は統合し、矛盾する値は利用者が選んでから移します。同一実体への重複書込、自己import、循環を避け、再実行でも節やimportを増やしません。

更新前から手動起動限定の方針がある場合は、利用者が置換を明示するまで保持します。主要5工程の自動続行へ移行するときも、変更するのは起動方針の該当箇所です。

## 完了を判断する根拠

実装はタスクのDone whenと受入条件を検査し、レビューは別セッションで行います。独立レビューの手段がなければ引継ぎを用意し、未完了と報告します。自分の見直しを独立レビューの成功には数えません。

仕様・計画の未承認、範囲変更、検査失敗などは各工程の停止条件に従います。規制対象のシステムでは、別途必要な保証工程を維持してください。

配布の静的検査、製品上の起動、実際の本文参照、作業の成功はそれぞれ別の証拠です。現行版の確認範囲は [対応範囲と制限](compatibility.md)を参照してください。導入から試す場合は [小さな変更の練習](getting-started.md)、中断後は [再開ガイド](work-resumption.md)へ進めます。

## バージョンとリリース

16スキルを1つの版として扱い、gitタグ `vX.Y.Z` で配布します。npmには公開しません。利用先での版固定と更新は [READMEのバージョン](../README.md#バージョン)を参照してください。

スキルの削除・改名、起動区分、成果物の書式やstatus、スクリプトの引数・終了コードの互換を壊す変更は破壊的変更です。SemVerに従い、試用段階の0.xではマイナー、1.x以降ではメジャーを上げます。

mainへのpush後、CIの決定的検査と配布検査が成功すると、semantic-releaseがコミットから版を決め、タグ・GitHub Release・CHANGELOG更新を作成します。手作業でタグは作りません。

| コミット | 版の扱い |
|---|---|
| `fix:` | パッチ |
| `feat:` | マイナー |
| `BREAKING CHANGE:` | 破壊的変更。0.xではマイナー |
| `docs:`・`test:`・`chore:` | リリースしない |

設定は `release.config.cjs`、ツールの固定版は `package.json` と `package-lock.json` にあります。1.0.0へ移行するときは `releaseRules` のbreaking用の行を外し、通常のメジャー更新へ切り替えます。

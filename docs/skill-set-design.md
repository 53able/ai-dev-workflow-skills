# ains スキル群の設計方針

## 目的

目的・制約・受入条件を先に決め、その範囲の実装と修正をAIに任せる。人は仕様、計画、差分、展開の判断を持つ。この進め方を、利用者が覚えることを最小にした形で提供する。ains は、規制対象のシステムで規制が求める保証工程を代替しない。

## 原則

1. **入口は ains。** Claude Code は `/ains`、Codex は `$ains`。 状況を見て次に使うスキルを示すルーターを1つ置く。
2. **起動者で分ける。** 流れを進めるスキルは利用者が明示起動する。Claude Code は `disable-model-invocation: true`、Codex は `policy.allow_implicit_invocation: false` を使う。起動制御は操作権限や承認とは別で、Codex の文脈節約量は保証しない。エージェントが自分で手を伸ばす必要がある規律だけをモデル起動にし、説明には用途を簡潔に書く。
3. **1スキル1成果。** 各スキルは明確な成果物と完了条件で終わり、全スキルを導入した上で各段階を使い分けられる。個別導入の保証はしない。順序はルーターが示すが強制しない。
4. **成果物は最小。** 変更ごとに spec（目的・制約・受入条件・対象外、承認の status）と tasks（方針・任せる範囲・停止条件・タスク・メモ）。検証結果は PR 本文へ。承認の状態欄は spec と tasks の status だけに置き、段階ごとの状態欄とゲート表は持たない。
5. **確認は判断点1回ずつ。** 人の承認は spec と tasks の status、/ains-ship の質問の3か所（小さな変更は2か所）。人が仕様、計画、差分、展開を確認するという元の実務フローに合わせるためだ。外向き操作の規則は Agent skills 節の1か所に置く。人の確認点は「ここで聞く」という手順にする。判断点は最大3つ、各々に推奨案を付け、「はい」で進められるようにする。事実はAIが調べ、決定は人がする。
6. **設定は一度。** `/ains-setup` がテストコマンド、必須レビュー規則、文書の置き場所、止まったときの相談先を「Agent skills」節に記録し、以後は聞かない。新しく書くときは AGENTS.md に書き、CLAUDE.md からは読み込む。
7. **本文は短く。** 肯定形で書き、中核語を繰り返し使い、1つの意味は1か所に置き、一部の分岐だけが使う詳細は別ファイルへ出す。
8. **自前で完結。** 質問、TDD、レビューの規律も ains 内に持ち、他のスキル群に依存しない。

## 目標値

- 説明は用途が伝わる長さに抑える。文脈節約量や常時可視性は保証しない
- 利用者が覚えるスキル：1つ（`/ains`）
- 変更ごとの成果物：5ファイル → spec と tasks（小さな変更は spec 1枚）

## 配布と互換性の境界

共有の SKILL.md 本文に小さな製品別の宣言設定を添える。現行の10段階・6規律は成果と再利用の境界に基づく構成であり、将来の数を固定する要件ではない。依存する兄弟スキルも必要なので、配布契約は全スキルのプロジェクト導入とする。導入コマンドは [README](../README.md#導入) にまとめる。

Agent skills 設定の正本は AGENTS.md、Claude Code 側は CLAUDE.md の `@AGENTS.md` import とする。CLAUDE.md だけの既存節は承認済みの値を保って移し、無関係な文章は保持する。同一設定の重複は統合し、矛盾は人が選ぶまで上書きしない。同一実体には一度だけ書き、自己 import・循環を作らず、再実行でも節や import を増やさない。これは実装の契約であり、移行ケースの実製品検証は [互換性文書](compatibility.md) に別途記録する。

質問 UI が利用できなければ短いテキスト質問を1つ出して回答を待つ。独立したレビューの実行手段がなければ別セッション向けの引継ぎを作り、レビュー未完了とする。自分の見直しを独立レビューの合格にしない。既に同じ範囲で得た判断は保持し、仕様変更では計画の承認を無効にする。

実行時の assets、scripts、参照 Markdown、agents 設定は各スキル内に残す。開発用 eval は `tests/evals/<skill>/` に分離し、ケース内の相対パスと実行モードを維持する。共通本文・製品設定の静的整合と、製品上の起動・設定・仕様・計画・実装・レビュー・出荷の実証は別の検証である。対象の Claude Code / Codex も実行時の証拠が揃うまでは正式サポート確認済みとしない。他エージェントと macOS 以外は未検証。

## ネイティブ起動と通常参照の設計

手動段階の抑止は、製品ネイティブのスキル起動に限定する。現行ソースは旧来の通常読み込み禁止と説明・本文への重複した制限を撤去済み。16役割（10手動段階・6自動規律）と全スキル導入を維持し、自動規律は簡潔な用途で発見できるようにする。

通常の Read/Bash、内容検索、手順・資産・テンプレート・補助スクリプトの参照利用は、依頼と権限の範囲で行え、追加承認は不要。明示段階の依存手順、スキルの説明・調査・編集、元の範囲を保つ独立セッションへの引継ぎも使える。参照はホストの操作権限、仕様・計画の承認、外向き操作の許可を付与しない。推薦や approved の状態は次段階のネイティブ起動指示ではなく、利用者が明示して続行した同じ範囲では再び許可を求めない。

検証では、実際のコマンドが製品にネイティブ認識された証拠と、正しい配置先本文を消費した証拠を分ける。成功した通常 Read は本文消費を示せるが、注入の証拠にはならない。完全な非公開実効プロンプトを普遍的に要求せず、製品が公開する native イベント・展開マーカー、正確な入力、固定版の選択経路と配置先来歴を使う。

質問の目標契約は、実際の構造化質問ツールを使う場合だけ UI 上限内かつ最大5問、それ以外の平文は未決1判断と回答待ちである。setup/spec の局所制約にも実装済みで、「あわせて」や追記にも別判断を含めない。実行結果は個別の検証で確かめる。最大3点の承認要約は解決済みの選択に限り、未決事項を束ねない。設定移行の正本・import・同一実体・矛盾時の選択、既存権限の保持、保存 I/O 要件、計画承認の無効化、独立レビューと人の判断は変更しない。

旧通常消費基準での Claude の直接読み込み・補助手順実行は歴史的 FAIL のまま残し、修正後 PASS と読み替えない。現在の native 起動限定基準では、その通常参照自体は失敗条件ではない。Codex の過去の観測不足と有限な強い対照合格も当時の事実として保持する。説明予算や参照禁止の実験は現在の設計ではなく、ファイルアクセスを遮断するセキュリティ保証も行わない。

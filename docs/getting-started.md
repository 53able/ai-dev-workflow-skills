# はじめてのains：小さな修正を仕様からレビューまで進める

使い捨てのPythonプロジェクトで、仕様の承認、テスト先行の修正、独立レビュー、出荷資料の確認を試します。最後はマージ・展開せずに止めます。Gitとターミナルを使える開発者向けです。

必要なのはPython 3、Git、Node.js 22.20以降、npm/npx、bash、導入・認証済みのClaude CodeまたはCodexです。ainsは試用段階です。[確認済みの範囲](compatibility.md)を確認してから始めてください。

## 1. ターミナルで練習用プロジェクトを作る

次をまとめて実行します。業務プロジェクトを使う必要はありません。

```bash
trial_dir=$(mktemp -d "${TMPDIR:-/tmp}/ains-first-use.XXXXXX")
cd "$trial_dir"
git init -q
cat > counter.py <<'PY'
def next_count(value):
    return value + 1
PY
cat > test_counter.py <<'PY'
import unittest
from counter import next_count

class CounterTest(unittest.TestCase):
    def test_zero(self):
        self.assertEqual(next_count(0), 1)

    def test_positive(self):
        self.assertEqual(next_count(2), 3)
PY
printf '__pycache__/\n' > .gitignore
python3 -m unittest discover -v
```

`Ran 2 tests` と `OK` が出れば準備できています。失敗したらPythonの版、現在のディレクトリ、作成した2ファイルを確認してください。

差分を見るための基準をローカルに保存します。名前・メールはこの練習用コミットだけに使います。

```bash
git add counter.py test_counter.py .gitignore
git -c user.name='ains tutorial' -c user.email='ains-tutorial@example.invalid' -c commit.gpgsign=false commit -m 'Add tutorial baseline'
git rev-parse HEAD
pwd
```

表示されたコミットIDとプロジェクトの絶対パスを控えます。リモートの設定は不要です。

## 2. 練習先へ全スキルを導入する

ターミナルは練習用ディレクトリのままにします。下のソースパスを、手元にある本リポジトリの絶対パスへ置き換えて実行してください。

```bash
npx --yes skills@1.7.4 add /absolute/path/to/ai-dev-workflow-skills --list
npx --yes skills@1.7.4 add /absolute/path/to/ai-dev-workflow-skills --skill '*' -a claude-code codex -y
npx --yes skills@1.7.4 list -a claude-code codex
```

16スキルの導入を確認し、この練習用ディレクトリから使う製品を起動します。以降のコマンドは**製品の会話欄**への入力です。

| 用途 | Claude Code | Codex |
|---|---|---|
| 現状と次の工程を見る | `/ains` | `$ains` |
| 初回設定 | `/ains-setup` | `$ains-setup` |
| 一連の作業を依頼する | `/ains 依頼文` | `$ains 依頼文` |

まず `/ains` または `$ains` だけを送ります。ファイルを変えず、初回設定を案内すれば想定どおりです。

## 3. 検査と任せる操作を設定する

`/ains-setup` または `$ains-setup` に、次の文を添えて送ります。

> 練習用プロジェクトです。検査は `python3 -m unittest discover -v`、変更記録は `docs/changes/`。任せる操作はこのディレクトリ内の編集とローカル検査だけです。コミット、外部送信、push、PR作成、マージ、デプロイは任せません。人の確認規則の案を示し、不明点は質問してください。

質問に答え、`AGENTS.md` の「Agent skills」節、`CLAUDE.md` の参照、人の確認規則を読みます。検査コマンドと操作範囲が依頼に合っていれば了承します。

既存設定に「各工程は手動起動のみ」とある場合は保持されます。承認後の自動続行を使うなら、「起動方針を、この変更について承認後に主要工程を続行する方式へ置き換える」と明示してください。操作権限の変更とは別に扱います。

## 4. 仕様を作り、内容を承認する

`/ains` または `$ains` に、次の依頼文を添えて送ります。`<基準コミットID>` は手順1で控えた値へ置き換えます。

> 内部関数 `next_count` で、負の整数を渡したとき返り値が0未満にならないようにしたいです。`-2` と `-1` は0、既存の0は1、2は3のままにしてください。この変更1件を仕様から実装・独立レビュー・ローカル出荷資料まで進めてください。整数以外の入力、永続化、外部連携は対象外です。小さな変更としてspec内に方式・タスク・メモを置き、仕様全体の承認を待ってから実装してください。承認後は同じ範囲で工程を続行してください。レビューの基準は `<基準コミットID>` です。結果は変更ディレクトリのpr.mdへまとめ、出荷判断を待ってください。任せる操作は編集とローカル検査だけです。コミット、外部送信、push、PR作成、マージ、デプロイは任せません。

質問に答えた後、`docs/changes/<日付-slug>/spec.md` を開きます。承認前は `status: draft` のままです。

- **受入条件**：4入力の期待値が依頼と一致する。
- **対象外と方式**：既存の内部関数を最小変更し、標準unittestを使う。依存や外部操作を追加しない。
- **タスクとDone when（完了条件）**：回帰テストの失敗を確認してから実装し、既存を含む全テストを通す。

問題があれば修正を依頼します。よければ「このspec全体と記載した方式・タスクを承認します。操作範囲はローカル編集と検査だけです」と返信します。記録が `status: approved` になったことを確認してください。

この練習は小変更なので、別のtasks.mdを作る工程を省きます。大きな変更では、仕様とは別にtasks.mdの方針・順序・任せる範囲も承認します。

## 5. 修正とテストの結果を確かめる

一連の作業を依頼しているため、承認後は実装へ進みます。工程ごとのコマンド再入力は不要です。AIが負数の回帰テストを先に失敗させ、その後に関数を修正し、全テストを通したか確認します。

ターミナルでも実行してください。

```bash
python3 -m unittest discover -v
git status --short
git diff -- counter.py test_counter.py
```

4入力を検査する全テストが成功し、specのタスクに `[x]` と完了条件の検証結果があれば実装を確認できます。件数はテストの分け方で変わるため、件数だけでなく内容を読みます。未追跡の新規ファイルは `git diff` に出ないので、`git status` に出たファイルも開いてください。

## 6. レビューと出荷資料を読み、ここで止める

実装後は、同じ依頼のまま独立レビューと出荷資料作成へ進みます。別セッションでのレビューが利用できない環境では、引継ぎ資料と「独立レビュー未完了」を示して止まります。その場合は引継ぎ先で実際にレビューを終えるまで出荷へ進めません。

変更ディレクトリの `pr.md` で、受入条件ごとの証拠、独立レビューの結果、未検証の点、人の確認者、戻し方を読みます。人の確認を判定するスクリプトの結果は次の意味です。

| 判定・終了コード | 次にすること |
|---|---|
| `NO_MANDATORY_MATCH` / 0 | 規則への一致なし。リスク・CI・操作許可の確認は残る |
| `HUMAN_REQUIRED` / 10 | 表示された領域の確認者が承認するまでマージしない |
| `UNVERIFIED` / 3 | 判定不能の理由を確認して人へ回す |

今回の基準コミットには確認規則がないため、規則の新設で10になる場合もあります。10はテスト失敗ではなく、3は「問題なし」ではありません。

資料と差分を確認したら、「資料は確認した。マージ・展開は行わずここで止める」と返信します。`pr.md` の存在だけで出荷完了にはなりません。未解決のレビューや人の判断があれば、その状態を残して終了します。

## 止まったときの戻り先

| 状態 | 対処 |
|---|---|
| スキルが見つからない | `pwd` と導入一覧を確認。利用先へ全スキルを導入してから製品を起動し直す |
| specがdraftのまま | 未決事項と仕様全体を確認し、承認または修正を返す |
| テストが失敗する | 期待した回帰テストの失敗か、修正後の失敗かを確認。出力を残して実装工程で直す |
| 同じ原因で3回失敗する／範囲外の操作が必要 | 試したことと必要な判断を確認し、範囲を決め直すまで止める |
| 仕様を変えたい | specと既存tasksをdraftへ戻し、変更内容を承認してから実装を再開する |
| 新しい会話で再開したい | 同じディレクトリでspec・tasks・メモを読ませ、`/ains` または `$ains` で状態を見る。続行は対象の変更ディレクトリと実行範囲を指定する |
| 複数の変更がある | 実行対象を1つ指定する。「最新」という状態表示だけで実行対象は決まらない |
| 旧設定により工程間で止まる | 手動限定の起動方針を確認し、移行するならsetupへ置き換えを明示する |

作者の補足が必要だった箇所は[初見利用の記録用紙](first-use-check.md)へ残せます。終わったら練習先であることを `pwd` で確認し、製品を終了してください。

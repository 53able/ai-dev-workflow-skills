# 小さな変更を通して試す

Git・ターミナルと Claude Code または Codex の導入・認証ができ、AI開発には不慣れな開発者向け。実際の業務リポジトリに触れる前に、使い捨ての練習用プロジェクトで、仕様→実装→出荷判断待ちまで進める。

これは練習手順であり、この文書の作成を初見の人による利用成功と数えてはいない。[現在の確認範囲](compatibility.md)も読む。

## 1. 練習用プロジェクトを作る

以下は**ターミナル**で実行する。Python 3、Git、[READMEの導入前提](../README.md#導入)が必要。自分の業務プロジェクトでは実行しない。

```bash
trial_dir=$(mktemp -d "${TMPDIR:-/tmp}/ains-first-use.XXXXXX")
cd "$trial_dir"
git init -q
cat > counter.py <<'PY'
def next_count(value):
    return value + 1
PY
cat > test_counter.py <<'PY'
import unittest
from counter import next_count

class CounterTest(unittest.TestCase):
    def test_zero(self):
        self.assertEqual(next_count(0), 1)

    def test_positive(self):
        self.assertEqual(next_count(2), 3)
PY
printf '__pycache__/\n' > .gitignore
python3 -m unittest discover -v
```

期待する結果は `Ran 2 tests` と `OK`。失敗したら先へ進まず、Pythonの版、カレントディレクトリ、上の2ファイルを確認する。ここでは既存の振る舞いを固定している。

基準点をローカルコミットにする。次の名前・メールは**この使い捨て練習専用の識別情報**で、設定はこのコマンドだけに適用する。業務リポジトリでは自分のプロジェクトの方針を使う。

```bash
git add counter.py test_counter.py .gitignore
git -c user.name='ains tutorial' -c user.email='ains-tutorial@example.invalid' -c commit.gpgsign=false commit -m 'Add tutorial baseline'
git rev-parse HEAD
pwd
```

表示されたコミットIDと絶対パスを控える。この基準点からの差分を最後に見る。リモートは作らない。

## 2. ainsを導入し、設定を確認する

**この練習用ディレクトリをcwdにしたまま**、[READMEの「別のプロジェクトで使う場合」](../README.md#導入)に従って全スキルを導入する。ソース側のパスは、手元の ains チェックアウトの絶対パスへ置き換える。ソースをcwdにした `add .` は、ここへの導入にはならない。

導入一覧に16スキルが見えることを確認し、このディレクトリから使う製品を起動する。以降の `/ains-*` と `$ains-*` は**製品の会話欄**に入力する。シェルのコマンドではない。使う製品の列だけを選ぶ。

| 段階 | Claude Code | Codex |
|---|---|---|
| 現状と次の工程を見る | `/ains` | `$ains` |
| 初回設定 | `/ains-setup` | `$ains-setup` |
| 仕様と小変更のタスク | `/ains-spec` | `$ains-spec` |
| 実装 | `/ains-build` | `$ains-build` |
| 出荷資料と判断 | `/ains-ship` | `$ains-ship` |

まず現状確認のコマンドを送る。次に、初回設定の対応スキルコマンドと以下の依頼文を、同じ会話メッセージで送る。

> 練習用プロジェクトです。検査は `python3 -m unittest discover -v`、変更記録は `docs/changes/`。AIに任せる操作はこのディレクトリ内の編集とローカル検査だけです。コミット、外部送信、push、PR作成、マージ、デプロイは任せません。人の確認規則の案を示し、不明点は質問してください。

人は `AGENTS.md` の Agent skills 節、`CLAUDE.md` の参照、人の確認規則を読む。検査コマンドと操作範囲が上と一致するか、無関係なファイルへの変更がないかを確かめて、内容を了承する。利用者が答えた同じ範囲の判断を何度も承認する必要はない。スキルが見えることや設定を了承したことは、新たな操作権限を与えない。

## 3. 仕様を作り、人が承認する

仕様の対応スキルコマンドと以下の依頼文を、同じ会話メッセージで送る。

> この練習用の内部関数 `next_count` で、負の整数を渡したとき、返り値が0未満にならないようにしたいです。`-2` と `-1` は0、既存の0は1、2は3のままにしてください。整数以外の入力、永続化、外部連携は対象外です。小さな変更としてspec内に方式・タスク・メモを置いてください。まず仕様案を作り、承認を待ってください。実装はまだ始めないでください。

AIは `docs/changes/<日付-slug>/spec.md` をdraftで作る。質問に答えたら、最後に**仕様全体**を確認する。人が見る点は次の3つ。

- 受入条件：上の4入力と期待値を検査すること。負の値の扱いをAIが勝手に広げていないか。
- 対象外と方式：既存の内部関数を最小変更し、標準unittestを使う。新しい依存・外部操作を加えないか。
- タスクとDone when：新しい回帰テストの失敗を確認してから実装し、既存を含む全テストが成功すること。

問題がなければ、例えば「このspec全体と記載した方式・タスクを承認します。操作範囲は先ほどのローカル編集と検査だけです」と実際に返信する。不一致ならその箇所を直してもらう。承認後に `status: approved` となったファイルを確認する。

今回はspecにタスクを含む小変更なので、`ains-tasks` は呼ばない。通常の大きな変更では、別のtasks.mdで方針・順序・任せる範囲を判断する。

## 4. テスト先行で実装する

実装の対応スキルコマンドと対象のspecのパスを、同じ会話メッセージで送る。推奨されたことや `approved` の表示だけで次の手動段階が始まるわけではない。

AIが新しい負数のテストを先に実行して失敗を確認し、関数を修正し、全テストを通すことを確かめる。テストが失敗したまま「完了」になっていたら進めない。

ターミナルでも次を確かめる。

```bash
python3 -m unittest discover -v
git status --short
git diff -- counter.py test_counter.py
```

期待する結果は、4入力の振る舞いを検査する全テストの成功、specのタスクの `[x]` とDone whenの実行結果。テスト件数はAIの分け方で変わりうるため、件数だけでなくテスト内容を読む。specや新しいファイルは未追跡の場合があるので、`git status`に出たファイルも開く。

## 5. 出荷資料を読み、判断待ちで止める

出荷の対応スキルコマンドと以下の依頼文を、同じ会話メッセージで送る。`<基準コミットID>` は最初に控えた実際のIDへ置き換える。

> 対象はこの練習変更です。レビューの基準は `<基準コミットID>` です。独立レビュー、検査結果、人の確認の要否を示し、外部PRではなく変更ディレクトリのpr.mdへまとめてください。push、PR作成、マージ、デプロイは行わず、必要な人の判断を待ってください。

AIは実際の別コンテキストへspec・差分・周辺コード・検査結果を渡してレビューする。利用環境で独立実行できなければ、引継ぎ資料と「独立レビュー未完了」を示して止まる。同じ会話で役を変えた自己レビューを合格にしない。引継ぎ資料があるだけで次へ進めない。

人の確認の判定は次のように読む。手動で規則を眺めるだけでスクリプトの結果を代用しない。

| 判定・終了コード | 意味と次の行動 |
|---|---|
| `NO_MANDATORY_MATCH` / 0 | 規則への一致なし。リスク評価とCI・操作許可の確認は残る。自動マージの許可ではない |
| `HUMAN_REQUIRED` / 10 | 規則に一致。表示された領域の確認者による承認までマージしない |
| `UNVERIFIED` / 3 | 規則なし・差分なし・取得失敗などで判定不能。理由を読み、人へ回す |

この練習ではsetupで規則を新設するため、基準コミットに規則がないことによる10も正常な人待ちである。終了コード10はテスト失敗とは違い、3も「問題なし」ではない。

人はpr.mdの受入条件ごとの証拠、独立レビュー結果、未検証・残る懸念、確認者、変更の戻し方を読む。コードは控えた基準点との差分と新規ファイルまで確認する。今回は練習なので「資料は確認した。マージ・展開は行わずここで止める」と判断できる。

**pr.mdがあるだけではship完了ではない。** 未解決のレビューや人の判断が残れば、その状態で止める。実業務では必要な承認・CI・操作許可が揃うまでマージしない。

## 困ったときと再開

| 見えた状態 | 確かめること／再開先 |
|---|---|
| スキルが見つからない | `pwd`とREADMEの導入一覧を確認。利用先へ一括導入したか確認してから製品を起動し直す |
| specがdraftで実装が止まる | 未決事項と仕様全体を確認。承認が済んだ同じ範囲なら記録を示し、未承認なら実際に回答する |
| テストが失敗する | コマンド・出力・失敗理由をspecのメモへ残す。期待したREDか、修正後の失敗かを区別し、buildで対応する |
| 同じ原因の失敗が3回続く／範囲外の操作が必要 | 他タスクへ進めず停止。試したことと必要な判断を相談先（未設定なら自分）へ示す |
| 仕様を変えたい | specと既存tasksの承認はdraftへ戻す。変更後の内容を再確認してから実装へ戻る |
| 会話をやり直す | 新しいセッションを練習ディレクトリで開き、specとメモ、あればtasksを読ませて `/ains` または `$ains` で次を確認する |

迷ったら `AGENTS.md` の変更の置き場所と `docs/changes/` を見る。作者の補足が必要だった箇所は[初見利用の記録用紙](first-use-check.md)へ残す。終わったら `pwd` で練習先を確認して製品を終了する。業務リポジトリのファイルやグローバル設定を戻す操作は、この練習には必要ない。

機械で確かめられることを先に済ませ、人には判断だけを渡す。人の確認時間がいちばん希少だからだ。結果は PR 本文の雛形 [assets/pr-body.md](assets/pr-body.md) に集める。

## 1. 決定的な検査

型、lint、テスト、秘密情報と依存の検査のうち、プロジェクトにあるものをすべて実行する。失敗したら ains-tdd で直して再実行する。直す範囲は ains-build と同じ（spec の受入条件と対象外、Agent skills 節と tasks.md の任せる範囲の中）。試行の上限と停止条件は ains-build に従い、ship の検査全体を1単位として数え、メモ（tasks.md、小さな変更は spec.md）に `ship 失敗 n/上限` と残す。範囲外の修正が要るなら止まる。通らない検査が残る変更は先へ進めない。

## 2. 受入条件ごとの証拠

spec.md の受入条件を1つずつ、書かれた検証方法で確かめ、pass / fail / 未検証 と証拠を書く。

- テストが受入条件を本当に主張しているかを読む
- 出力の文字列一致ではなく、要求した振る舞い（形式、性質、境界）で判定する
- すべての条件の期待結果を、利用者の操作、業務知識、既存の契約のいずれかと照らし、照合元を書く。仕様とテストは同じ誤解から作られうる。照らせなかったものは未検証にする
- 画面操作や業務フローに関わる変更は、実際の操作や業務責任者の確認が要るかを書く。テストが通ることと、利用者の問題を解くことは別だ
- Agent skills 節に現行仕様の置き場所があれば、変わった振る舞いを同じ PR で現行仕様に反映する

## 3. レビューと判定

- ains-review で別セッションのレビューを行い、指摘を選別する。独立レビューが未完了なら、引継ぎ資料と未完了の理由を残し、レビュー済みとして先へ進めない
- ains-review-gate で人の確認の要否を判定する

## 4. 展開を計画する

利用者に見える変更、高リスクの変更、戻らない状態変更を含む変更は、ains-release-safety で展開と切戻しを計画する。

## 5. PR と人の判断

PR 本文を埋める。PR の作成と push は、Agent skills 節の外向き操作の規則で許されたときに行う。許す規則が無ければ（Agent skills 節も tasks.md の任せる範囲も無い場合と、規則が人の指示を求めていてその指示が無い場合を含む）、本文の下書きを変更ディレクトリの `pr.md` に保存して示し、push と PR 作成をしなかった理由を応答に書く。理由は、許す規則が無いこと、または規則が許していない箇所（Agent skills 節か tasks.md の任せる範囲の該当箇所）である。

同じ範囲で既に明示された許可・判断は引き継ぐ。追加の判断が必要なら ains-grilling の質問手順と上限に従う。構造化質問ツールが使えるときは1回にまとめ、平文では1つずつ聞く。

- 受入条件の fail・未検証と、実際の操作や業務責任者の確認が要るもの（確認者と時期）
- 人の確認が必須な変更と、確認してほしい人
- 展開の方法と止める基準（該当する場合）

マージとデプロイは、ains-review-gate のマージの条件がそろったときに行う。merge で本番展開が始まる構成では、展開の判断も merge の前に得る。

## 完了条件

PR 本文（または pr.md）がすべて埋まり、人がマージと展開を判断した。

# 規則外の変更のリスク評価

## 前提

- route-review.sh の必須規則に一致しなかった変更だけを評価する
- 評価するのは「人の確認がどれだけ要るか」だけ。書き方や正しさは評価しない（それは ains-review の役割）
- 評価器は人の確認を足せるが、必須規則による確認を外せない

## 手順

1. 変更ファイルのパスを先に読み、どの領域か把握する
2. 変更の中身を次の観点で見る
   - 影響範囲：共有ライブラリ、中核データモデル、多くの呼出し元を持つ関数か
   - 可逆性：戻せば元に戻るか、状態や外部への影響が残るか
   - テスト：触れたコードに意味のあるテストがあるか
   - 差分の大きさ
   - 頻繁に壊れる、または障害を起こしたことのあるファイルか
3. 確信が持てない観点があれば、高い側へ切り上げる

## 出力

```json
{
  "risk": "low | medium | high",
  "recommendation": "auto_merge | one_human | multiple_humans",
  "reviewer_domain": "例：決済、フロントエンド、データ基盤",
  "what_could_go_wrong": "1〜2文",
  "reason": "判断の根拠。どの観点からそう言えるか"
}
```

`auto_merge` は、チームが自動統合の段階を許可し、Agent skills 節に例外として書いた場合にだけ使う。それ以外は `low` でも人が統合を判断する。

## 例の整え方

過去のレビューから「人の確認が不要だった変更」と「必要だった変更」を数件ずつ選び、この評価器の例として追記する。例：文言の小さな修正は low、新しい公開APIの追加は high（外部の利用者が依存し、後から変えにくいため）。

## 評価器の見直し

人が評価と異なる判断をしたら、`docs/ains/override-log.md` に記録する（ains-retro が読む）。

| 偏り | 兆候 | 調整 |
|---|---|---|
| 緩すぎる | 人が評価を覆して確認を追加することが続く | 観点や例を厳しくする |
| 厳しすぎる | 人が高リスク判定の変更をそのまま通すことが続く | 狼少年になり読み飛ばされるため、例を足して絞る |

## 自動化の段階

評価器の権限（記録のみ → 助言・規則の執行 → 低リスク経路の自動化）の広げ方は ains-harness で決める。チームが自動統合を許可するまで、評価は助言として示す。

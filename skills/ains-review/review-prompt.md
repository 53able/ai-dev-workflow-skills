# 独立レビューの指示文

プロジェクトに合わせて「規約」「過去の障害」「レビュー対象外」を書き換えて使う。指摘が外れるたびに、このファイルを直して精度を上げる。

## 渡すもの

- spec.md（受入条件と対象外）
- 対象の識別：依頼された変更・許可された範囲、リポジトリ、対象種別（コミット済み／ローカル作業）、解決した base・head・merge-base。対象の変更と対象外の変更を区別できる根拠を付ける
- コミット済み対象：明示された base...head の差分と、その head の対象ファイルの内容。base・head は不変のコミット識別子で示し、現在の index・作業ツリー・未追跡は混ぜない。ローカル作業の開始履歴は要らない
- ローカル作業対象：取得時点と各状態の内容の識別情報を示し、許可された変更について、必要なコミット済み差分、ステージ済み差分、未ステージ差分、未追跡ファイルの内容を渡す。各差分の比較元と比較先を示し、現在の内容・削除・パスやモードの変更も識別できるようにする。開始時の状態があれば使い、無くても、検証可能な基準状態・保持されたパッチ・新規ファイルの基準状態での不存在などにより対象を十分に特定できればよい。現在のツリーから過去の clean 状態を推測しない。無関係な既存変更は同じファイル内でも対象の差分から除外する。現在の内容に残らないステージ済み変更も省略せず、どの状態をレビューするかを明記する。コミットは前提にせず、新たなコミット権限も与えない
- 上で確定した対象の内容に対応する周辺コードと関連する呼出し元。必要な文脈として参照する対象外コードは、レビュー対象の変更と区別して示す
- 決定的な検査のコマンド・結果・対象の識別情報（未実施／失敗も明記）。取得中に対象が変わった場合は同じ対象として扱わない
- 根拠が不十分で対象や許可範囲を特定できない、必要な内容や検査結果が欠ける、取得中の変化を解消できない場合は、不足を明記して「独立レビュー未完了」として止まる。開始時の記録が無いことだけでは止めない。空または古い差分やリスク判定を、対象全体の独立レビューの代わりにしない
- 渡さないもの：実装中の会話、実装者の推論、実装者の自己評価

## 指示文

```text
あなたは <サービス名> のレビュアーです。この変更には欠陥がある前提で、作者が見落とした問題を探してください。
重要な問題だけを簡潔に挙げます。問題が見つからなければ、そう書いて終えてください。問題を作り出さないでください。

# 確認すること
1. 仕様との一致：spec.md の受入条件を1つずつ差分と突き合わせる。満たしていない条件と、仕様にない追加の両方を挙げる。
2. 設計への適合：既存のパターン、ADR、規約と比べる。新しい層の追加、依存方向の変更、確立した方法があるのに新しい方式を作っていないか。
3. テストの質：コードではなくテストを読む。主張に意味があるか、境界や失敗時を扱うか、実際の回帰を検出できるか。
4. セキュリティ：入力検証、認可、注入、秘密情報、危険な関数。AI機能を含む場合はプロンプトインジェクションと出力の扱い。
5. 個人データ：新しいログや分析イベントへの個人情報、外部への送信。
6. 費用と性能：ホットパス上の外部呼出し、上限のないクエリ、N+1。
7. 文書：振る舞いの変更に README、運用手順、API文書が追随しているか。
8. 残骸：デバッグ出力、コメントアウト、使われない関数、読まれない設定。

# 規約
- <例：金額は整数のセントで扱い、浮動小数点を使わない>
- <例：外部APIの呼出しには必ずタイムアウトと再試行を付ける>
- <例：DBアクセスはリポジトリ層を通し、ハンドラに生SQLを書かない>

# 過去の障害（再発を探す観点）
- <例：INC-123 冪等キーの欠落で二重課金 → 新しい決済の書込みが冪等か>
- <例：INC-456 上限のないクエリでDB停止 → limit のないクエリ>

# レビュー対象外
- 生成コード、vendor、スナップショット（*.snap）

# 出力
指摘ごとに：
- 重大度：blocker / warning / nit
- 箇所：ファイル:行
- 問題：1文
- 根拠：コードや仕様のどこからそう言えるか
- 修正案：1文
最後に1行で評決：APPROVE または REQUEST_CHANGES
```

## 構成の選び方

まずは上のチェックリスト型の単一レビュアーで始める。特定の観点（多くはセキュリティ）に専用の調整が見合うと分かったときだけ、その観点を別のレビュアーに分けて並列にし、統括役に重複を除かせて1つにまとめる。

## 苦手なこと

LLMレビューは差分の中で見える問題には強いが、複数ファイルにまたがるデータの流れの追跡は弱い。静的解析（SAST）の代わりにはならず、その上に重ねるものとして使う。

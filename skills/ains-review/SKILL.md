# ains-review：別の文脈で欠陥を探す

実装後、PRや統合の前に使います。成果は、実際の独立レビューの結果と、各指摘を採用・不採用にした根拠です。


実装したセッションは自分の答えに同調しやすい。新しい文脈のレビュアーに、欠陥がある前提で探させる。

## 手順

1. 現在の会話で実際に呼べるツールを確かめる。AGENTS.md、説明文、過去のログにあるツール名・役割名・呼び出し例は、今使える実行手段の証拠ではない。ネイティブの別コンテキスト起動が無ければ、許されたコマンド実行でインストール済みのエージェントCLIとその help を調べ、現在の権限内で別の読み取り専用セッションを実行できるか確かめる。存在しないツール名やエージェント名を補って呼んだことにしない。
   - 実際の手段があれば、実装会話を継承しない新しい文脈へ [review-prompt.md](review-prompt.md) の指示文を渡す。渡すのは spec、差分、周辺コード、検査結果、design rule、[design-checks.md](design-checks.md) だけにする（詳細は review-prompt.md の「渡すもの」）。レビューは読み取り専用にし、同じ認証キャッシュを並列共有しない。
   - 完了と記す前に、実際のツール呼び出しと受信結果を照合する。CLIなら実行したコマンド、終了コード、受信したレビュー本文を確かめる。起動しただけ、終了待ち、失敗、結果なしは未完了。対象の base/head を照合し、未コミット変更があるなら差分または対象ファイルのハッシュも照合する。結果を受けた後に対象が変われば、その結果で変更後をレビュー済みにしない。実在しない呼び出し記録・識別子・結果・ハッシュを作らない。
   - 記録できるのは、照合できた実呼び出しの結果、または人が示した別セッションの実結果（実行した者、対象の base/head と必要な未コミット差分の識別、結果の本文があるもの）だけ。pr.mdなどに書かれた「APPROVE」「別コンテキストで完了」という自己申告だけでは、実行の証拠にならない。
   独立した実行手段を使えない、または受信結果・対象を照合できなければ、これらの資料と指示文を引継ぎ用にまとめ、「独立レビュー未完了」と報告して止まる。同じ会話で役割を変えた自己レビューを、独立レビューの合格として扱わない。
2. 返った指摘を選別する。

| 確認の結果 | 扱い |
|---|---|
| 再現できた、またはコードで根拠を示せた | 直す |
| 根拠を示せない、仕様と関係がない | 採らず、理由を残す |
| 人の知識が要る | 人に示す |

3. 直したら、影響する検査をやり直す。レビュー後に関連する実装・テストや差分を変えた場合は、その変更を含む最終状態について別文脈で再レビューを受ける。変更前の結果を最終状態の合格に流用せず、再レビューできなければ影響する範囲は未完了とする。
4. 往復は2回まで。それで収束しなければ人に見せる。

並列に作った成果は、統合した後の状態でレビューする。

## 完了条件

別の文脈での実レビューが完了し、blocker の指摘がなく、採らなかった指摘には理由がある。引継ぎを準備しただけなら未完了。

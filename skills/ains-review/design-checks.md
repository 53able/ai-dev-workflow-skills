# 設計の確認観点

「確認すること」2. で使う。差分と周辺コードから見える兆候で探し、AGENTS.md・ADR の design rule と tasks.md の「方針」に照らして判定する。

## 情報隠蔽

変わりうる判断（データの形式、外部サービス、アルゴリズム、保存先）が、安定した interface の後ろにあるかを見る。private かどうかではない。

- 公開メソッドが可変の内部状態（リスト、map、内部オブジェクト）をそのまま返す
- 呼出し元が内部表現（DB の行、外部 API の応答形式、内部の enum 値）を直接扱っている
- interface の signature に実装の都合（特定ライブラリの型、ORM のエンティティ）が出ている

## 依存

依存は変更の伝わる道筋だ。

- 逆流：下位の層（domain、core）が上位や外側（infra、UI、handler）を import する。design rule の依存方向に反する import
- 循環：パッケージやモジュールが互いを import する。差分で新しく循環を作る import
- 暗黙の依存：単位（秒とミリ秒、セントと円）、形式（日付文字列、ID の書式）、呼ぶ順序やタイミング、定数を、import なしに複数の場所が同じ前提で持つ。同じ値や変換を別ファイルに書き写した差分
- 片側だけの変更：一緒に変わるべきファイル（型と変換、スキーマとシリアライザ、送信側と受信側）の片方だけが差分にある

## パターンの誤用

- 意図なき模倣：実装が1つしかない Strategy、Factory、interface
- 名前だけのパターン：`XxxStrategy`、`XxxObserver` と名付けたが、差し替えも通知もしない
- 責務の肥大：パターンの1クラスに無関係な処理が集まる
- 過剰適用：変わらない部分にまで層や間接参照を足す
- 責務の割り当てとの混同：どこに置くかの問題を、パターンの導入で解こうとする

適用が正当なのは、明確な変更の型、安定した design rule、両側の独立した進化、明示的な分離の仕組みの4つがそろうときだ。spec、AGENTS.md、ADR の既存の規則を守るための port はこれに当たる。

## 構造の anti-pattern（差分で見える兆候）

| anti-pattern | 差分で見える兆候 |
|---|---|
| 不安定な interface | 広く使われる interface や基底クラスの signature を変え、呼出し元が多数一緒に変わる |
| モジュール性の違反 | 依存関係のない2つのモジュールが、同じ前提のために一緒に変わる |
| 不健全な継承 | 親が子の型を判定する、子が親の約束を破る（例外を投げる、引数を狭める）、利用者が子の違いを意識して分岐する |
| 相互依存の塊 | 新しい import で、複数のファイルが互いに参照しあう輪ができる |
| パッケージの循環 | パッケージ単位で互いを import する |
| 交差 | 1つのファイルに多くの依存元と依存先が集まり、そこを変えると広く波及する |

## 名前

- `Manager`、`Helper`、`Util`、`Handler`、`Processor` など、責務を語らない名前の新しい型やモジュール
- 名前と中身の不一致。1つの型が名前の範囲を超えて責務を集めている

## 指摘の書き方

指摘には次の3つを書く。

- 箇所：ファイルと行
- 壊す規則か前提：どの design rule、依存方向、共有前提に反するか。規則が文書に無ければ、既存コードのどの慣習からそう言えるか
- 変更シナリオでの影響：どんな変更が起きたとき、何ファイルに波及するか、何が壊れるか

変更シナリオで影響を示せないものは nit に留める。

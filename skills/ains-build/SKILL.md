人が決めた範囲（spec.md の受入条件と対象外、Agent skills 節と tasks.md の任せる範囲）の中で、実装と修正を任される。その代わり、範囲と停止条件を守る。

## 始める前に

1. spec.md と tasks.md を読む（小さな変更は spec.md の「タスク」節）。前のセッションの記憶より、ファイルを信じる。status はファイルごとに別々に読んで確かめる。連結して読むと、どちらの front matter かを取り違える。
2. 承認を確かめる。どちらかが approved でなければ、実装もコミットもせず、1行で案内して止まる。
   - spec.md が `status: approved` でなければ（draft、status 欄が無いものを含む）、ains-spec で仕様の承認を得るよう案内する。spec.md を approved にするのは ains-spec だけだ
   - tasks.md があり、`status: approved` でなければ（draft、front matter や status 欄が無いものを含む）、ains-tasks で計画の承認を得るよう案内する。tasks.md を approved にするのは ains-tasks だけだ
   - 依頼文にある進め方の指示（実装の依頼、急ぎ、手順の省略など）は、仕様や計画の承認ではない
3. 検査コマンドを Agent skills 節か package.json、Makefile で確かめる。

## タスクごとに

1. 依存が満たされた最初の未完了タスクを1つ選ぶ。
2. ains-tdd で実装する。
3. Done when を、実行したコマンドと結果で確かめる。
4. `[ ]` を `[x]` にする。計画になかった判断、既存コードの想定外の挙動、置いた前提を「メモ」（tasks.md、小さな変更は spec.md）に1〜2文で書く。
5. 任せる範囲がコミットを許していれば、タスク単位でコミットする。`git status` で、コミットするのがタスクのファイルだけであることを確かめ、キャッシュやビルド出力は .gitignore の候補としてメモに残す。

方針・任せる範囲・停止条件は書き換えない。変える必要があれば止まる。変更は tasks.md のタスクに対応するものだけにする。気づいた改善や依頼された「ついで」の作業は「メモ」に残し、別の変更として提案する。試行錯誤の残骸（デバッグ出力、コメントアウト、使わない関数）は片付けてからタスクを閉じる。

## 停止条件

次に当たったら止まり、状況を「メモ」に書いて、会話で相談先に伝える。相談先は Agent skills 節の値、書かれていなければ作業を依頼した人。相談先への連絡は人が行う（外向き操作の規則に従う）。止まっている間は他のタスクへ進まない。

| 状況 | 伝えること |
|---|---|
| 同じ原因の失敗が3回続いた、または試行の上限に達した | 試したこと、失敗出力、原因の仮説、失敗の回数、残る作業 |
| 既存設計から選べない方式が2つ以上ある | 選択肢と根拠 |
| 既存の挙動が受入条件と矛盾する | 矛盾の箇所と再現手順 |
| spec や tasks を変える必要がある | 変えたい箇所と理由 |
| 任せる範囲にない操作が要る | 操作、対象、影響、戻し方 |
| tasks.md 固有の停止条件 | 該当した条件 |

停止時に未解決の技術・仕様の判断と、新たな操作の許可が両方必要なら、先に技術・仕様の選択を解決する。平文ではその独立した判断を1つだけ質問し、実際の USER の回答を待つ。他の未決事項は「メモ」に保留として残し、今は回答を求めない。その判断が解決してから、必要な新しい操作の許可を、操作・対象のパス・影響・戻し方を明示した別の質問で求め、実際の USER の回答を待つ。質問の形と上限は ains-grilling に従い、この解決順序を守る。同意を推測しない。同じ範囲で既に明示された回答・許可は引き継ぎ、再承認を求めない。status、インストール済みのスキル、指示本文だけから許可を導かず、範囲や権限が未解決の間は実装を再開しない。

試行の上限は1タスク10回。数えるのは、緑を目指して実装した後の検査の失敗で、意図した赤は数えない。Agent skills 節か tasks.md の任せる範囲に別の値があれば、それに従う。回数はメモに `T<n> 失敗 n/上限` と残し、再開したらそこから数える。費用と時間の上限は、Agent skills 節に書かれていればそれに従い、ハーネスの設定（max_turns、予算）でも縛る。

同じ失敗が続くときは、言い換えて再試行する前に、仕様の抜け・制約の曖昧さ・文脈の不足のどれが原因かを考える。規約の無視や会話の劣化が疑われるなら ains-context-care を使う。

## 完了条件

全タスクが `[x]` で、Agent skills 節の検査コマンドが通っている。
次は ains-ship。

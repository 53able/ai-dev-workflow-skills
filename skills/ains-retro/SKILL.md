モデルが同じでも、周りの規約、テスト、仕様が育てば出力は良くなる。今回の発見を、次の変更が読む場所へ戻す。

## 1. 振り返る

「メモ」（tasks.md、小さな変更は spec.md）、PR のレビュー指摘、展開後の観測、`docs/ains/override-log.md`（あれば）を読み、5つに答える。

1. 仕様は要件を捉えていたか。実装中に見つかった要件は何か
2. 方針は途中で変わったか。変わったなら、なぜか
3. Done when は適切だったか。緩すぎる・厳しすぎるものはなかったか
4. 毎回補足が要った注意（ライブラリの方針、命名、規約）はあったか
5. 次に仕様化する価値のあるものは何か

## 2. 戻す先を決める

| 発見 | 戻す先 |
|---|---|
| 機能の現在の振る舞い | 機能単位の現行仕様（`docs/specs/<機能>.md` や `openspec/specs/`）。ains-ship が同じ PR で反映しきれなかった分を扱う。変更ごとの spec.md は履歴として残す |
| 全体の設計判断、不変条件 | ADR、AGENTS.md / CLAUDE.md。1規則1制約、理由つき |
| 繰り返す作業の手順 | スキル、スクリプト |
| 再発させたくない不具合 | 回帰テスト |
| 機械で見つけられる誤り | lint、アーキテクチャ検査、`docs/ains/human-review-rules` |
| レビューで繰り返した指摘 | ains-review の review-prompt.md の規約・過去の障害 |
| 次の変更候補 | チケット |

昇格させるのは方法と原則。一度きりの実装の詳細は昇格させない。規則と人の確認の規則の追加・削除は、差分で示して人が承認する。

## 3. 本番障害から始めるとき

1. 直近の展開、エラー、トレース、ログを集め、時系列と原因の仮説を複数出す。各仮説に根拠と反証の材料を添え、確定は人に任せる。
2. 本番の入力とエラーから、修正前のコードで**赤**になる再現テストを書く。
3. 修正は新しい変更として ains-spec から通す。修正も同じ検査、レビュー、人の確認、展開の安全策を通る。
4. 仕組みのどこで止められたかを書き、2. の表で戻す。

## 4. AIの判断との差

人がレビュー指摘やリスク評価を覆したら、`docs/ains/override-log.md` に1行ずつ足す（日付、変更、AIの判断、人の判断、理由）。同じ方向の上書きが続いたら規則と指示文を調整する。人が確認を足し続けるなら緩すぎ、指摘を無視し続けるならノイズが多すぎる。

## 完了条件

5つの問いに答え、戻した先（ファイルと PR）を示した。

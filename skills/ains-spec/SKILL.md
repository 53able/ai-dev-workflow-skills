AIに任せる範囲を、実装の前に人が決める。spec.md は「何を作るか」「何を壊さないか」「何をもって完了か」に答え、作り方は書かない（それは ains-tasks）。

## 1. 置き場所を作る

AGENTS.md / CLAUDE.md の「Agent skills」節にある変更の置き場所を使う。節が無ければ既定の `docs/changes/` を使い、あとで ains-setup を勧める。ains-tasks などから差し戻された既存の変更なら、そのディレクトリの spec.md を使い、下の new-change.sh は実行しない。

```bash
<このスキルのディレクトリ>/scripts/new-change.sh <slug> [--root <dir>]
```

OpenSpec や Spec Kit を併用するリポジトリでも、spec.md と tasks.md はこの変更の置き場所（既定 `docs/changes/<id>/`）に置く。道具の文書との役割の分け方は [sdd-tools.md](sdd-tools.md) にある。

## 2. 分岐を判断する

- **受入条件が書けない**（技術的に可能か、利用者に合うか、部門間で認識が揃っているか、モデルの振る舞いが分からない）→ [prototype.md](prototype.md) で時間を区切った試作を設計し、結論を持って戻る
- **既存の振る舞いや依存が分からない** → [existing-system.md](existing-system.md) で観測された契約と特性テストを先に用意する
- **SDDの道具を選びたい** → [sdd-tools.md](sdd-tools.md)

## 3. 質問する

質問の形と上限は ains-grilling に従う。既に明示された回答・承認は引き継ぐ。

ains-grilling で、目的、制約、受入条件、対象外、境界の入力、失敗時、同時操作、既存データの扱いを聞く。最後の「この理解でよいか」の確認は、5. の承認と兼ねる。コードと資料で分かることは先に調べ、ains-context-care の「実装前の文脈ブリーフ」を「文脈」に書く。

## 4. spec.md を書く

- **受入条件**は1項目ずつ「検証」に検査方法を書く。永続化を伴う変更では、保存成功後の再読込、読込エラー、入力検証の拒否、実際の書込・保存 I/O 失敗を別々に扱う。保存失敗を不正入力や壊れたデータの読込エラーで代用しない
- 保存 I/O 失敗について、利用者に見える結果（成功と表示しない、失敗を通知するなど）、直前の保存済み状態・保存できなかった入力の保持／回復方針を受入条件に書く。検証は妥当な入力で永続化先への書込失敗を起こし、通知と失敗後の再読込・状態を確かめる。業務上の扱いが未決なら勝手に決めず、「未決事項」にその方針と検証方法を残して承認前に解決する
- 金銭・データ・セキュリティ・外部連携に触れるなら、**失敗時・並行操作・観測・切戻し**の受入条件を1件ずつ入れる
- 制約は具体値と理由で書く。数値や振る舞いで書けない語（「適切に」「高速に」）は置き換える
- 対象外を書き、「ついでに」直す範囲を閉じる
- 技術選択、ファイルパス、関数名は tasks.md に回す。小さな変更では、採る方式を「タスク」節の「方式：」行に書く
- 1〜3ページに収める
- 「任せる」と答えた点は仮定として書く

小さな変更（1セッションで終わり、公開インターフェースも共有基盤も触らない）は、spec.md の「タスク」節にタスクも書き、ains-tasks を省く。それ以外は「タスク」「メモ」節を削る。

## 5. 承認を得る

「未決事項」が残っていれば、承認を求めず、3. の手順で次の判断を質問する。未決の判断を要約に混ぜて一括承認を求めない。

「未決事項」が空になり（最後の回答を仕様に反映した結果を含む）、同じ内容・範囲の明示的な承認がまだ無ければ、同じターンで仕様案全体の承認を求める。

- 解決済みの内容（受入条件の境界、対象外の線引き、確認済みの仮定。小さな変更では「方式：」行）を3点以内に要約する
- その内容で仕様案全体を承認することを推奨し、承認を求める質問を1つだけ行う。別の未決判断や実装許可の質問を足さない
- 個別項目の更新報告だけでターンを終えない。「今回は個別判断だけの回答」「実装許可はまだ与えない」という回答は、承認を尋ねることの禁止ではない。利用者が承認の質問自体を後にするよう明示したときだけ従う

承認は次のように扱う。

- 同じ内容・範囲について既に明示された承認は引き継ぎ、再承認を求めない
- 新たに人が承認したら `status: approved` にする
- 仕様の内容・範囲を変えたら spec.md を draft に戻し、既存の tasks.md の status も draft に戻す。古い計画の承認を残さないためだ。承認待ちの間は古い計画で実装を進めず、変更後の仕様と計画を確かめ直す

## 完了条件

spec.md が `status: approved` で、受入条件すべてに検証方法がある。
次は ains-tasks（小さな変更なら ains-build）。

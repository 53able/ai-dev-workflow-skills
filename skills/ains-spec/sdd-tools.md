# SDDの道具の選び方

各道具の機能やコマンドは変わりやすい。採用前に各プロジェクトの現行ドキュメントを確認する。

## 位置づけ

| 道具 | 重さ | 仕様のまとめ方 | 向く | 向かない |
|---|---|---|---|---|
| OpenSpec | 軽い | 現行仕様（`openspec/specs/`）と、変更ごとの差分仕様（`openspec/changes/`）。出荷後に差分を現行仕様へ統合しアーカイブ | 長く続く既存システムへの小さな変更の積み重ね | 深いドメインモデリングが要る新規開発、強制力のある段階ゲート |
| GitHub Spec Kit | 中間 | プロジェクト共通の原則（constitution）と、機能ごとの spec / plan / tasks | 中〜大規模の新機能、GitHub中心のチーム | 既存システムの小さなバグ修正 |
| BMAD Method | 重い | 専門役割（分析、PM、設計、開発など）が PRD、アーキテクチャ、ストーリーを作って引き継ぐ | 大規模な書換え、既存システム内の新サービス、監査証跡が要る規制業界 | 即時の修正、一人開発、速度優先 |

どれも仕様の陳腐化を自動では解決しない。実装時の変更を仕様へ反映し、レビューでずれを確認する運用が要る。

## ains と併用するときの役割

| 文書 | 置き場所 | 持つもの |
|---|---|---|
| ains の spec.md | `docs/changes/<id>/` | 目的・受入条件・仕様の承認 |
| ains の tasks.md | `docs/changes/<id>/` | 実現方法・タスク・計画の承認 |
| 道具の現行仕様 | `openspec/specs/` など | 統合後の振る舞い |
| 道具の変更文書 | 道具の変更ディレクトリ | spec.md へのリンク |

## 選ぶときの問い

1. 新規か既存か。新規で複数人・長期なら Spec Kit か BMAD。既存への小変更が多いなら OpenSpec
2. チームが維持できる手続きの量。その道具の成果物が、次のレビューの週まで更新され続けるか。PRD・アーキテクチャ・エピックを生きた文書として保てないなら、重い道具は選ばない
3. エディタ・エージェントの構成が揃っているか
4. 誰が保守しているか。変更履歴を見て、手順が頻繁に変わる道具に深く結びつけすぎない
5. 監査・データ管理の要件

比較に時間をかけすぎず、1つ選んで小さな変更で試す。合わなければ、小さな変更の結果を根拠に見直す。

## constitution・常設ルールの書き方

禁止だけを書くと、学習データでその書き方が一般的な場合に無視されやすい。禁止、理由、代わりにすることを1組で書く。

```markdown
### 3. 金額は整数のセントで扱う（必須）
浮動小数点で金額を計算しない。丸め誤差で請求額がずれるため。
代わりに `src/money/Cents` 型を使い、表示時にのみ書式化する。
```

## 差分仕様の書き方（OpenSpec 形式に合わせる場合）

```markdown
## ADDED Requirements
### Requirement: <名前>
システムは <振る舞い> しなければならない（SHALL）。

#### Scenario: <名前>
- **WHEN** <条件>
- **THEN** <結果>

## MODIFIED Requirements
### Requirement: <名前>
<変更後の要件全文>。<制約の理由を一言>

## REMOVED Requirements
### Requirement: <名前>
**Reason**: <廃止の理由>
**Migration**: <代わりの手段>
```

## チケットとの関係

仕様をチケットに複製しない。チケットは「どんな仕事で、誰が担当か」、仕様は「その仕事の意味と作り方」を持つ。チケットIDを変更ディレクトリ名か spec に入れ、チケットからは spec へリンクする。

# 既存システムの変更：Spec Islands

リポジトリ全体の仕様を復元しようとしない。近く変更する箇所だけを、変更の前に仕様化する。仕様のない海に、変更ごとに島ができていく。

## 1. 優先する島を選ぶ（チームで導入するとき）

| 観点 | 優先が高い |
|---|---|
| 変更頻度 | よく変わる |
| 影響範囲 | 中核データモデル、共有ライブラリ、主要APIハンドラ |
| 知識の偏り | 理由を知る人が一人か二人 |
| 予定 | 近く大きな変更がある |
| 安定性 | テストが厚く変更予定もない箇所は後回し |

変更頻度と影響範囲がともに高い箇所から始める。

## 2. 現状の振る舞いを説明させる

対象の機能に関わるファイルをまとめて読み、次を説明する。改善案は出さない。目的は現状の正確な記述だ。

- 主な責務
- コードから読み取れる、強制している制約
- 主なエラー条件
- 意図的かもしれない、自明でない振る舞い

1ファイルずつではなく、機能単位でまとめて読む。ファイルごとの説明になってしまい、機能としての振る舞いが見えなくなるからだ。

この説明は、コードから推した草案であり、元の設計意図ではない。バグや回避策の名残を、意図として自信ありげに書くことがある。人が確認するまで草案として扱う。可能なら別のセッションに説明とコードを渡し、食い違いを指摘させる。

## 3. 暗黙の契約を押さえる

文書にないが、他の箇所が依存している振る舞い（エラー形式、並び順、出力の書式）を探す。

1. 呼出し元を調べる（`grep`、言語サーバーの参照検索）。変更の経緯は `git log -L` や blame と関連 PR で、名前の分からない関連箇所は意味検索で探す。各呼出し元が何に依存しているかを書く。表示用に見えて、別の処理が再パースしている出力などは見落としやすい
2. 対象を変える前に既存テストを実行する。薄ければ特性テストを書く。特性テストは、正しい振る舞いではなく現状の振る舞いをそのまま記録するテストだ。契約を誰も知らなくても、変えてしまったことを検出できる
3. spec.md の「観測された契約」に列挙する。意図ではなく観測だと明記し、変えるなら呼出し元の確認が要るという合図にする

### 特性テストの書き方

- 代表的な入力と境界の入力を選び、現在の出力をそのまま期待値にする（スナップショットやゴールデンファイルでもよい）
- テスト名かコメントに「現状の記録。仕様として確認済みではない」と書く
- 既知の不具合を記録した場合は、そのテストに印を付け、spec.md の受入条件で直すか、対象外にするかを決める

## 4. 守る仕様と既知の不具合を分ける

観測した振る舞いを3つに分け、人に確認する。

| 分類 | 扱い |
|---|---|
| 守る仕様 | 受入条件か制約へ。特性テストはそのまま残す |
| 既知の不具合 | 今回直すなら受入条件へ。直さないなら対象外へ |
| 不明 | 未決事項へ。人が答えるまで変えない |

## 5. 常設の知識へ戻す

調べる過程で分かった設計判断や全体の制約は、変更ごとの spec ではなく、ADR や常設ルールへ移す（ains-retro）。変更ごとの spec は統合後に履歴となり、全体の知識は常設文書に蓄積していく。

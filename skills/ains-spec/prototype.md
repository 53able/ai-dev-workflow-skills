# 試作（スパイク）の設計と、仕様への引継ぎ

仕様は既知のことしか書けない。確信のない要件を文章で作り上げるより、先に試して確かめる。AIで使い捨ての試作は安くなった。目的は速さではなく、早く確かめることだ。

## 試作が要る不確実性

| 種類 | 例 |
|---|---|
| 技術的な実現性 | ライブラリがこのデータ形状を扱えるか、APIが負荷下で公称どおり動くか、予算内に収まるか |
| 製品の方向 | 画面や操作の形が決まらず、利用者の反応を見ないと書けない |
| 部門間の認識のずれ | 先に仕様を書くと一部門の見方が前提になってしまう |
| 非決定的な振る舞い | モデルが中心の機能で、実際の応答を見ないと受入条件が書けない |

次の場合は試作を省き、仕様を書く：小さなバグ修正、理解済みモジュールの定型変更、類似機能で方式が検証済み、製品の方向に関係者が合意済み。

## 試作を始める前に決めること

試作ブランチの最初のコミットメッセージに書く。

```markdown
# SPIKE: <問い>

- 問い：この試作が答える1つの問い（例：設定の保存は JSONB 列と別テーブルのどちらが、問合せと項目追加に有利か）
- 判定方法：何を見れば答えが出たとするか（例：主要クエリの JOIN 数、項目追加時の移行の要否）
- 上限：時間 / 費用（例：2時間）。超えたら打ち切って人に報告する
- 置き場所：prototype/<名前> ブランチ、または別ディレクトリ
- 捨てるもの：試作のコード全部
```

## 試作中

- 品質基準は問いに答えられる最低限でよい。ハードコードしてよい
- 上限に達したら、答えが出ていなくても止めて報告する

## 試作の後

試作は答えを得た時点で役目を終える。コードを読み、仕様を書き、新しいブランチで作り直す。試作の近道を本番に残さず、仕様を確かめた事実から書くためだ。

試作を読んで次の4問に答え、仕様と計画へ振り分ける。

| 問い | 行き先 |
|---|---|
| 何が証明されたか | spec.md の「文脈」と目的 |
| 何が未解決か（制約、境界、失敗の仕方） | spec.md の制約・受入条件・未決事項 |
| 関係者は何に合意したか | spec.md の「文脈」（再議論を避けるため） |
| 残す価値のあるパターンは何か | tasks.md の方針（spec には書かない） |

試作の結果、作らないと決まることもある。それも結論として spec.md の「文脈」に残す。

# 常設ルールの棚卸し基準

## 規則が増えると、全体の遵守は落ちる

規則ごとの遵守率を p、規則数を N とすると、全規則を同時に守る確率は概ね p^N になる。p=0.95 なら5規則で約77%、20規則で約36%。網羅的な30規則より、焦点の定まった10規則の方が守られやすい。

## 常設に残すかの判定

| 問い | 弱い場合の行き先 |
|---|---|
| 最も頻繁なタスクで、出力に測れる差を生むか | 「時々」ならスキルか参照文書 |
| 無かったら何が壊れるか | 「まれに」「特に何も」なら削除候補 |
| ツールやCIで既に強制されているか | 強制されていれば削除 |
| 手続き的な形式（引数、出力構造）か | ツール説明・スキルへ移す |
| 同じ不変条件を守る別の規則があるか | 統合する |

## 規則の書き方

- 1規則に1制約。理由を添える。
  - 例：日付処理は date-fns を使う。moment は保守終了しており、バンドルも大きくなるため。
- 「適切に」「なるべく」のような判定できない語を避ける。
- 条件があるものは、条件を先に書く。EARS 記法の型が使える。
  - 常時：システムは X する
  - 事象：Y が起きたとき、X する
  - 状態：Y の間、X する
  - 望ましくない状況：Y の場合、X する
- 抽象度は、行動を導ける具体性と、想定外の場面で判断できる余地の間に置く。全場面を個別に列挙すると脆くなり、抽象的すぎると推測を強いる。

## 環境文脈に入れる項目

新しく参加した人に最初に渡す情報を、エージェント向けにしたもの。

- 実行環境とバージョン、主要な依存
- ディレクトリ構成と「ここから読む」入口
- 従うアーキテクチャのパターンと、参照すべき実装例
- 共通の検査コマンド（型、lint、テスト）と、完了前に実行する範囲
- 触れてはいけない領域、人の確認が必須の領域（`docs/ains/human-review-rules` を参照させる）

スタックや規約を変えたら同じPRで更新する。人のオンボーディング文書も兼ねる。

## スキルとルールの区別

- ルールは制約（例：入力はスキーマライブラリで検証する）
- スキルは手順（例：新しいAPIエンドポイントを追加する一連の作業）
- 副作用のある手順（メール送信、デプロイ）は、モデルが自動で起動しない設定にする

出力が悪いときは、言い回しより先に「何が入っていて、何が欠けていたか」を疑う。

## 規約が守られないとき

上から順に確かめる。上ほど安く確かめられ、指示を足しても直らない原因だからだ。

1. **読み込まれたか**：ルールファイルの未読込、スキル未起動、別ディレクトリの設定
2. **どこにあったか**：長い会話の中ほどや大量のツール結果の後ろに埋もれていないか
3. **目立っていたか**：長いルールファイルの奥の一文になっていないか
4. **矛盾していないか**：別の規則、ツール説明、過去の依頼、既存コードの慣習
5. **失われていないか**：会話の圧縮で落ちていないか

| 原因 | 直す場所 |
|---|---|
| 未読込 | 設定や配置。規則は足さない |
| 埋没・目立たない | 規則を短くして上位へ移す、または spec の制約へ書く |
| 矛盾 | 一方を消し、残す方に理由を書く |
| 圧縮で欠落 | 引継いで新しいセッションで始める（下記） |
| 本当に未記載 | 1規則だけ足す（理由つき） |

## 引継ぎ

序盤に合意した制約に反する出力、同じ失敗の繰り返し、目的からの逸脱が出たら、会話を続けるより引継ぐ。

1. 変更ディレクトリの「メモ」（tasks.md、小さな変更は spec.md）に、決定と理由、残作業、試して失敗したこと、未解決の質問を書く。後の判断を左右する決定は必ずファイルへ書く。
2. 新しいセッションで spec.md と tasks.md を読ませ、重要な制約を冒頭で確かめさせる。

## 実装前の文脈ブリーフ

触れる領域の既存パターン（参照する実装1〜3件）、守る契約（API、スキーマ）、使う既存部品（認証、ロガー、エラー型）、依存のバージョンと参照した文書の出所・更新日を集め、spec.md の「文脈」に書く。監査ログや論理削除のように、コードに現れない規約は人に聞く。

## 常設ルールの整理

AGENTS.md、CLAUDE.md、ルールファイルを整理するときは [rules-audit.md](rules-audit.md) を読む。規則の追加・削除は人が承認する。

## 完了条件

原因と直す場所が1つに決まっている。決められない場合は、確かめたことを残して人に示している。

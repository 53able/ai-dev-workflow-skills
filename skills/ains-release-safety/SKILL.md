展開は制御された実験として扱う。問題が起きても、影響が小さく、すぐ見え、戻せる形にする。

## 手段を選ぶ

| 手段 | 使う場面 |
|---|---|
| feature flag（既定は無効） | 利用者に見える変更、本番前に試しにくい変更。デプロイと公開を分ける基本の手段 |
| 段階公開（例：1% → 5% → 25% → 全体） | 状態を持たないアプリの変更。各段階を指標で進める・止める |
| 利用者区分ごとの公開 | 社内 → 希望者 → 1地域 → 全体。区分ごとに許容できるリスクが違うとき |
| blue-green | 無停止で確実な退路が要る大きな変更 |
| shadow（本番入力で実行し応答は捨てる） | 入力の分布が心配な書換え。副作用のない経路だけ |

使い終えたフラグの削除までを、機能の完了とする。

## 戻らない状態変更

DB移行、送信、課金、削除、メッセージ消費は、アプリを戻しても戻らない。デプロイとは別の運用イベントとして、次を計画に書く。

1. 互換：新旧どちらのアプリでも動く期間を作る
2. 分離：スキーマ変更、データのバックフィル、アプリの変更を別々のリリースにする
3. 拡張してから縮小：新しい構造を足す → 使うコードを出す → 安定後に古い構造を消す
4. 冪等：再試行されても二重送金・二重送信・重複データを起こさない
5. メッセージ：順序、処理できないメッセージ、デッドレター、再処理を決める
6. 進捗の観測：件数、エラー、速度、一時停止と中止の手段
7. 前へ直す：戻せない前提で、是正の変更として進める手順

「5分後に戻したら何が起きるか」を書き出し、戻せない箇所は 3. の形に組み直す。

## 観測と止める基準

- ログ、メトリクス、トレースをそろえる。新しく計装するなら OpenTelemetry で共通の形式にする
- 許容する信頼性を SLO で数値にし（例：99.5% のリクエストが 500ms 未満）、許容できる失敗の量（エラーバジェット）を出す
- バジェットが残れば出荷を続け、尽きたら止めて安定化を優先する
- アラートは利用者が感じる症状とバジェットの消費速度で出す
- 初回公開後、決めた指標と業務指標を数時間見て、結果を「メモ」（tasks.md、小さな変更は spec.md）に書く。止める基準に達したら計画どおり止めるか戻し、原因を戻す次の手順として ains-retro を人に勧める（この提案だけでネイティブ起動しない）

## 完了条件

選んだ手段、止める基準、切戻し手順、戻らない状態変更への対処、展開後に誰が何を見るかが書かれている。

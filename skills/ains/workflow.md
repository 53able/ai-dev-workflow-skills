# 実行範囲と工程の続行

ains-setup / ains-spec / ains-tasks / ains-build / ains-ship に共通する手順。

## 依頼を引き継ぐ

- `ains` の状態確認だけの依頼では、次の工程を案内するだけで、ファイルを変更しない。
- 利用者が一連の作業を依頼したときは、その依頼と対象の変更を引き継ぐ。対象が一意に決まらなければ編集前に1つ質問し、最新の変更を実行対象に決めない。承認済みのファイルがあることだけでは新しい作業を始めない。
- 工程を単独で依頼されたときは、その工程の完了条件までを行い、次を案内する。一連の作業も依頼されている場合だけ、次の工程へ進む。
- 既存の AGENTS.md / CLAUDE.md に各工程の明示起動を求める規則があれば保持する。現利用者がその規則を変更すると明示した範囲だけを優先し、更新されたスキルや一般的な実行依頼だけから規則の撤回を推測しない。設定移行が必要なら ains-setup で起動方針だけの変更案を示し、判断を待つ。

## 次へ進む

一連の作業を依頼されていれば、現在の工程の完了条件と次の工程の前提を確認し、次の SKILL.md を読んで実行する。製品が提供するスキル起動手段が利用できれば使い、なければ同じ本文・資産を参照して手順を実行する。通常参照をネイティブ起動の証拠とは呼ばない。手段の差だけを理由に、利用者へ各工程のコマンド入力を求めない。

- setup → spec → tasks → build → ship。小さな変更は spec の方式・タスクを承認してから build へ進む。
- 仕様・計画の承認が必要なら案を示して回答を待つ。実際の承認を同じ内容・範囲のファイルへ記録したら、元の一連の依頼を続ける。工程を起動してよいかを重ねて聞かない。
- 未承認、未決事項、範囲変更、検査失敗、独立レビュー未完了など、各工程の停止条件を守る。仕様変更では spec と既存 tasks を draft に戻し、古い承認で実装しない。工程の自動続行は承認の代わりにならない。
- 編集・検査・コミット・push・PR・マージ・デプロイの許可は、既存の任せる範囲で個別に判断する。起動設定や工程の続行から操作権限を増やさない。
- ship は検証と独立レビューの結果をまとめ、出荷の判断が未解決なら待つ。ローカル資料までの依頼なら、許された資料を仕上げて止まり、公開操作を追加しない。retro は明示依頼時だけ行う。

新しい状態ファイルや承認欄は作らない。対象と依頼の範囲は会話と既存の変更成果物から引き継ぎ、再開時に不明なら推測せず確認する。

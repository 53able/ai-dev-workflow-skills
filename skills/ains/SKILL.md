入口は Claude Code の `/ains`、Codex の `$ains`。各工程も単独で呼べる。起動設定は操作の許可や業務上の承認を与えない。

## 1. 依頼と状況を見る

- AGENTS.md / CLAUDE.md の「Agent skills」節と既存の起動方針
- 変更ディレクトリの状態：`<このスキルのディレクトリ>/scripts/status.sh [<変更の置き場所>]`
- 利用者の依頼が状態確認か、一連の作業の実行か

**状態確認**：引数なし、「今どの段階か」「次は何か」、説明だけの依頼では、次に使うスキルと理由を示す。ファイルを変更せず、コミットしない。対象が指定されていなければ、最新の変更を推奨の対象にする。各スキルを説明するときは、その SKILL.md を読む。

**実行依頼**：「この変更を進めて」「実装からレビューまで」など、一連の作業が明示されていれば、[実行範囲と工程の続行](workflow.md) に従い、2. で決まる工程を実行する。対象は指示された変更、または依頼内容から一意に特定できる変更とする。複数候補があり対象を決められなければ、編集前に対象を1つ質問して回答を待つ。最新という理由だけで実行対象を選ばない。

setup/spec/tasks/build/ship はエージェントが呼び出せる。承認済みという表示やAIの推奨だけで、一連の実行依頼があったと扱わない。仕様・計画・出荷の判断と操作の権限は各工程で確かめる。既存の各工程明示起動規則も、利用者が変更すると明示するまでは保持する。

## 2. 主な流れ

アイデアを作って出荷するまで。上から順に見て、最初に当たるものを選ぶ。

1. Agent skills 節がない → `ains-setup`（リポジトリごとに1回）
2. 新しく作りたい・直したいという依頼で、既存の変更に当たらない → `ains-spec`
3. マージ・展開を終えた、または本番で問題が出たと利用者が言う → `ains-retro` を案内する。実行は明示依頼がある場合だけ
4. それ以外は、1. で選んだ対象の変更の状態で決める。状態確認で対象指定がなければ status.sh の先頭行（最新の変更）を使う。

| 対象の変更の状態（status.sh） | 次 |
|---|---|
| spec が draft | `ains-spec` |
| spec が approved、`plan=-`、`tasks=0/0` | `ains-tasks` |
| `plan=draft` | `ains-tasks`（計画の承認が先。タスクが完了していても同じ） |
| 未完了のタスクがある | `ains-build` |
| タスクが1件以上あり、すべて完了 | `ains-ship` |
| どれにも当たらない | status.sh の行を示し、次にしたいことを人に聞く |

小さな変更（spec の「タスク」節にタスクがあり `plan=-`）は、build か ship の行に当たる。

1行の修正やタイポは流れに乗せなくてよい。状態確認なら直し方と検査を案内し、修正を依頼されていれば許された範囲で直して検査する。マージ前の ains-review-gate の判定はこの場合も行う。

## 3. 流れの外

| 状況 | 使うもの |
|---|---|
| チームでAIの使い方を揃えたい | `ains-team-canvas` |
| レビュー待ちや不具合の流出が増えた、CIを見直したい | `ains-harness` |
| MCP や CLI をエージェントに使わせたい | `ains-tool-access` |

次のスキルは、エージェントが必要に応じて自分で使う。名前を指定して呼んでもよい。

| スキル | 役割 |
|---|---|
| ains-grilling | 質問で認識を揃える |
| ains-tdd | テスト先行の実装 |
| ains-review | 別セッションの敵対的レビュー |
| ains-review-gate | 人の確認が必須かの判定とマージ条件 |
| ains-release-safety | 展開、フラグ、戻らない状態変更 |
| ains-context-care | 規約無視の診断、引継ぎ、ルールの整理 |

## 完了条件

状態確認では次に使うスキルと理由を示した。実行依頼では指定範囲を終え、または必要な判断・停止条件と証拠を示して回答待ちにした。

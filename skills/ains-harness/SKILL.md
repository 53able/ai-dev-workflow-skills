コードを書く量が増えると、正しさを確かめて信頼する工程が律速になる。人の確認時間を最も希少な資源として扱い、機械で確かめられることを先に通してから人に渡す。仕組みは、安く速い層から順に入れる。

| 層 | 担うこと |
|---|---|
| 1. 決定的な検査 | 型、lint、テスト、秘密情報・依存・コードの脆弱性検査で不適合を止める |
| 2. LLMレビュー | 仕様とのずれ、設計の問題、テストの不足を探す |
| 3. 安全な展開 | フラグ、段階公開、切戻しで影響を抑える |
| 4. 実行時の観測 | ログ・メトリクス・トレース、SLOで本番の問題を見つける |
| 5. 人の判断 | 目的や高影響の変更を、責任を持つ人が確認する |

層は下から順に入れる。決定的な検査が固まる前にリスク評価や自動統合を入れると、不具合を速く出荷するだけになる。

## 1. 現状を調べる

1. CI設定、pre-commit、`package.json` などのスクリプト、ブランチ保護を読み、必須の検査と任意の検査を一覧にする。
2. 直近の不具合、切戻し、レビューで繰り返した指摘を、人に聞くかIssueから集める。
3. [gate-menu.md](gate-menu.md) と照らし、欠けている検査を挙げる。

## 2. 次に入れる1つを選ぶ

入れるのは一度に1つ。直近の不具合や手戻りを最も防げる1つを選び、人と合意する。

既定の順序：

1. テスト、strict な型検査、lint、秘密情報の検査を、1つのマージを止めるCIにまとめる。ローカルでも同じものを1コマンド（`make check` など）で実行できるようにし、AGENTS.md に書く
2. 独立したLLMレビュー（ains-review の `review-prompt.md` をプロジェクトの規約と過去の障害で調整）
3. 人の確認を必須にする規則（ains-review-gate、`ains-setup` で配置）と、規則外のリスク評価
4. 観測と自動化（SLO、段階公開、自動切戻し）。計装、SLO、フラグ、テストが揃ってから

多くのチームは 1〜2 に長く留まってよい。次の層は、今の痛みがそれを求めたときに足す。

## 3. 段階的に必須化する

既存の負債がある検査は、段階を踏んで必須にする。

- 一度まとめて掃除してから必須にする（未使用コード、型エラーなど。エージェントに向く作業）
- 掃除しきれないなら、まず報告だけにし、新しく増える違反だけを止める
- 閾値（脆弱性の重大度、性能予算）は現状付近から始め、徐々に締める

変更はPRとして出し、CI設定の変更は人が承認する。

## 4. 自動化の権限を段階的に広げる

LLMレビュー、リスク評価、自動統合は、次の段階で広げる。各段階は小さく戻せるようにし、根拠が崩れたら下げる。

| 段階 | AIがすること | 上げる根拠 |
|---|---|---|
| 記録のみ（shadow） | 判断に介入せず、判断していたであろう内容を記録する | 人の判断との一致率と、外れる方向が分かった |
| 助言・規則の執行 | 明確な規則（必須検査の失敗、必須規則の一致）でだけ統合を止める・人を割り当てる | 明確なケースで信頼できることが示された |
| 低リスク経路の自動化 | 検査を通過し低リスクと評価された変更（文言、社内ツール、テストの厚い非重要経路）だけ自動統合 | 自動統合分の不具合流出率と切戻し率を見続ける |

認証、課金、移行、基盤などの重大な変更は、どの段階でも人が確認する。

## 5. 仕組み自体を測る

PRの処理時間、人の確認時間、本番への不具合流出・切戻し・変更失敗、誤検知率、費用と遅延を併せて見る（採用する指標と担当は ains-team-canvas の合意記録へ残す）。処理時間と人の確認時間が下がり、流出と切戻しが横ばい以下なら、自動化が効いている。

次の兆候が出たら見直す。

| 兆候 | 対処 |
|---|---|
| レビューのコメントが返信なしで閉じられる | 誤検知率を測り、指摘を絞る |
| 重要な変更の承認が極端に短い | 人へ回す件数を減らし、届いたものに時間を使えるようにする |
| セキュリティ指摘が溜まり続ける | 新しい高重大度だけを止める |
| フラグが増え続ける | 削除を機能の完了条件に含め、経過日数を追う |
| 人が同じ方向にAIの判断を覆し続ける | 規則と指示文を調整する（`docs/ains/override-log.md`、ains-retro） |

## 6. 保守する

仕組みには保守担当（テックリードやプラットフォーム担当）を置く。新しい道具は、本番の重要経路や共有設定から離れた所で試し、結果（試したこと、効いたか、標準にすべきか）を短く共有し、採用したものだけを標準へ戻す。標準を固定したままにすると、各自が隠れて回避し始める。

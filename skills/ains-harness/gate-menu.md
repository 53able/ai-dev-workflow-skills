# 決定的な検査のメニュー

ツール名は例。すべてを入れるものではなく、痛みのある所から選ぶ。

| 検査 | 捕まえるもの・AIで悪化する理由 | 入れ方 |
|---|---|---|
| lint・整形 | セッションごとに書き方が揺れる | 設定をコミットし、pre-commit とCIの両方で。CIでは check モード |
| 型・コンパイル | 存在しないメソッド、引数の数や型の誤り、架空のフィールド。費用対効果が最も高い | strict を最大限に。既存エラーは一度解消してから必須化。移行中は新規エラーだけ止める |
| テスト | 同じエージェントがコードとテストを書くと、全行を通るが何も主張しないテストになりうる | カバレッジ率を品質の指標にしない。下の2つで質を見る |
| mutation testing | 生き残った変異 = テストが確かめていない箇所 | 遅いので、PRで触れたファイルに限る。決済・認証・中核ロジックに最低スコアを置き、そこから広げる |
| property-based testing | 明示されなかった境界（空、負数、Unicode、境界値） | 不変条件のある純粋なロジックに少数の性質（往復変換、冪等、金額の保存） |
| 静的解析（SAST） | 公開コード由来の脆弱なパターン（SQL連結、未エスケープ、危険なデシリアライズ、パストラバーサル） | 言語の標準ルールから始め、後でコードベース固有のルールを足す |
| 依存・コンテナ | 記憶にある古い・放棄されたパッケージ、既知の脆弱性 | lockfile とイメージの両方。high / critical で失敗。閾値は徐々に下げる |
| 秘密情報 | デバッグ中の直書き、テストデータへの実トークン、ログ出力 | pre-commit（手元で止める）とCI（hook は飛ばせるがCIは飛ばせない）の両方 |
| IaC | 公開バケット、公開DB、暗号化なし、過剰なIAM。機能テストでは見つからない | インフラのディレクトリ全体を、plan の前に。high で失敗 |
| アーキテクチャ適合 | 目の前のタスクのために層や境界を越える。積み重なると設計が溶ける | 本当に越えられたら困る境界を1〜2個から（ドメイン層からインフラ層への import 禁止、循環依存の禁止） |
| 性能・バンドル予算 | 1件ずつは軽微でも累積で膨らむ。削除より追加に傾く | 予算は現状付近に置き、回帰で止める |
| クエリ | N+1、索引漏れ、全表走査。小さなテストDBでは見つからない | N+1 検出、重いエンドポイントのクエリ数の上限、実行計画の差分 |
| 契約 | 「改善」としてフィールド名や型を変える | OpenAPI / Protobuf の新旧差分で破壊的変更を止める。利用側の契約テスト |
| アクセシビリティ・多言語 | ラベル欠落、コントラスト、キーボード操作、文字列の直書き | コンポーネントテスト・E2E に組み込む |
| 未使用コード・依存 | 試行錯誤の残骸 | 新しく増えた未使用を止める。既存は一度掃除 |
| PRの大きさ | 巨大なPR、無関係なリファクタの混入。人は大きなPRを流し読みする | 閾値（例：2,000行）を超えたら分割か理由を求める。指示でも「1PR = 1つの論理的な変更」とする |
| 依存の更新 | 古い依存の負債 | 低リスクの更新はまとめ、同じCIを通す |

## 最初の束

テスト、strict な型検査、lint、秘密情報の検査を、マージを止める1つのCIにまとめる。既存のツールを有効化して必須にする作業が中心になる。その先は、繰り返している失敗を防ぐ検査から1つずつ必須化する。

## エージェントの自己検査

エージェントがPRを作る前に、ローカルで同じ検査を1コマンドで実行し、通るまで直すようにする。そのコマンドを AGENTS.md に書く。画面のある機能では、ブラウザ操作のツールでE2Eの操作を実行させ、失敗を読ませる。

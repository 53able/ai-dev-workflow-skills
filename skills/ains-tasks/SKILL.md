spec の実現方法を、実装の前に人が確かめられる形にする。この段階ではコードを書かない。修正が最も安いのはここだ。

## 1. 調べる

1. spec.md が `status: approved` であることを確かめる。draft なら ains-spec に戻す。
2. 触れるコードを読み、従う既存パターン、使う既存部品、呼出し元を確かめる。
3. 仕様の不足や矛盾が見つかったら、spec.md の「未決事項」に書き、spec.md の status を draft に戻して ains-spec に戻す。tasks.md があれば、その status も draft に戻す。仕様の穴は仕様で埋め、spec が再承認されるまで tasks.md の承認を求めない。
4. 既存の tasks.md が approved で、承認された仕様・計画・任せる範囲が変わっていなければ、その承認を保持して完了条件を確かめる。書き直しや再承認は不要。
5. 既存の tasks.md が draft で、全タスクに Done when と AC があり、spec のすべての AC に対応するタスクがあれば、「3. 承認を得る」から始める。

## 2. tasks.md を書く

雛形 [assets/tasks.md](assets/tasks.md) を spec.md と同じディレクトリにコピーして埋める。既に tasks.md があれば、雛形の節を追記し、front matter を足さない。status があれば draft に戻す。

- **方針**：採る方式、乗る既存部品、検討して捨てた案と理由
- **任せる範囲**：Agent skills 節の既定から変えるときだけ書く。外向き操作を任せるなら、操作と範囲を明記する
- **停止条件**：決済、認証、移行など、この変更に固有のもの
- **タスク**：次の形で並べる

各タスクは1セッションで終わり、動作を確かめられる**縦の切り口**にする。「DB全体」「画面全体」ではなく「設定を保存し、読み戻して表示する」までを1つにする。

- **Done when**：計画全体を読まなくても判定できる、テスト合格か観測できる状態
- **依存**：先に終わるべきタスク。並列にできるものは「なし（並列可）」
- **AC**：対応する受入条件の番号。どのACにも対応しないタスクは対象外に踏み込んでいないか見直す

Done when に「かつ」が2つ以上ある、または別レイヤーの3ファイル以上に及ぶタスクは分ける。

並列化（サブエージェント、worktree、VM）を検討するときは [parallel.md](parallel.md) を読む。

## 3. 承認を得る

計画の承認はここだけで行う。質問は ains-grilling の手順に従い、回答を待つ。方式の選択、タスクの順序、任せる範囲の3点を示して承認を求め、人が直しを求めたら直して示し直す。高リスクの変更（認証、課金、データ移行、基盤、外部連携）では、ains-release-safety の観点で切戻しと戻らない状態変更への対処を方針に書いてから示す。

「確認なしで進めて」「最後まで進めて」のような依頼は計画の承認ではない。承認を求めずに先へ進まず、3点を示して回答を待つ。

人が承認したら、tasks.md を `status: approved` にする。front matter が無ければ、先頭に挿入する。

## 完了条件

tasks.md が `status: approved` で、全タスクに Done when と AC がある。
次は ains-build。

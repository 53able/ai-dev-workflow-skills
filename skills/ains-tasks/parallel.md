# 並列化と分担の判断材料

## 並列化を検討する兆候

- 1つの会話に文脈が収まらない
- 独立した作業が直列に待たされている
- 簡単な工程に強いモデルを使っている、または難しい工程に弱いモデルを使っている

## 並列化の代償

- 引継ぎには要約の誤りが入り、下流がそれをそのまま受け入れる
- 互換性のない選択が警告なく組み合わさり、完成して見えるが壊れた結果になる
- 調査の重複、マージの衝突、統合の手間
- トークン費用が大きく増える
- 人が確認できる量が上限になる。サブエージェントを使う作業の流れは、同時に3本程度までにする

増やす前に、統合後の結果を人が確認しきれるかを見る。

## サブエージェントの形

| 形 | 分割が決まる時点 | 向く仕事 |
|---|---|---|
| Orchestrator-worker | 実行時に統括役が調べてから決める | 影響範囲がまだ分からない変更 |
| Sequential pipeline | 事前に固定 | 前の成果を次へ渡す、依存のある仕事 |
| Fan-out / fan-in | 事前に既知 | 互いに独立した調査や検査を並べ、最後に集約する仕事 |
| Router | 1件ずつ実行時 | 入力を分類して、合う担当へ振り分ける仕事 |

共通して、統括役は1つにし、作業者は統括役へ報告する（作業者どうしで直接話させない）。統括役は要約しか見ないので、薄い要約や誤った要約に引きずられる。分けるのは、本当に大きいか本当に独立した仕事だけにする。

作業者どうしの調整は、共有ファイル（spec.md、tasks.md）で行う。この2つがディスク上の共有の黒板になり、セッションが切れても残る。

## 分け方（隔離）の種類

それぞれ防ぐ問題が違う。同じ隔離だと考えない。

| 単位 | 分けるもの | 使う場面 |
|---|---|---|
| 別セッション・サブエージェント | 文脈（記憶） | 読取り専用の調査、ログ・テストの読解。書き込むファイルが重ならない作業 |
| Git worktree | ディレクトリとブランチ | 別PRになる2つの変更を並行させる。`.env` など無視ファイルは引き継がれない |
| VM・コンテナ | 実行環境 | ビルドや環境破壊が他へ波及しうる作業、大量の並行作業 |

衝突を防げる最も軽い手段を選ぶ。

どれも、ホストの秘密情報や認証情報を守る権限隔離ではない。秘密情報や外部への副作用を扱うなら、実行環境の権限を別に絞り、取り込む側でも成果物を検査する。

## Advisor（相談役）

速いモデルが主な作業を進め、難しい設計判断や解けない不具合に当たったときだけ、問いと根拠をまとめて強いモデルへ相談する。難所が全体の一部に限られるときに成り立つ。毎回相談するなら、両方の費用を払うだけになる。

## 固定の手順か、動的な分担か

| 仕事の性質 | 進め方 |
|---|---|
| 毎回同じ順で行う検査・調査・移行 | スクリプトに固定し、各ステップでエージェントを呼ぶ。再現でき、安い |
| 対象によって手順が変わる一回限りの仕事 | 統括役に動的に分けさせる。柔軟だが結果が揺れる |

## モデルを選ぶ

ランキングではなく、自分のタスクで比べて選ぶ。

- 代表的なタスクを数件選び、候補のモデルで同じ Done when を満たせるかを試す
- 品質（検査の通過、手戻り）、遅延、費用を記録して比べる
- 難しい設計と定型編集で、同じモデルを使う必要はない

## 反復ループの安全装置

ループで回す場合（同じ指示を新しいセッションで繰り返す、目標達成まで続ける）は、次を tasks.md の「方針」に書く。

- 検査できる終了条件（例：auth 配下のテストがすべて通る、ビルドが警告なしで終わる）。「品質を良くする」は判定できない
- 反復回数の上限
- 完了の合図（決めた文字列を単独の行で出力したら終了、など）
- 1周ごとにテストを通してからコミットする
- 完了判定は作業者自身ではなく、別のモデルか検査に任せる。別のモデルでも同じ誤りをしうるので、決定的な検査を併用する

## 人の少ない自動化（dark factory）の前提

仕様と自動検査を入力に、途中の会話を減らして変更を作る進め方は、次の2つが事前に揃うときだけ使う。

1. 明確でテストできる仕様
2. 結果の正否を、人なしで判定できる自動検査

向くのは、定型のCRUD、テストの拡充、フレームワーク移行、再現手順が明確なバグ修正。新しい設計、誤りの代償が大きいシステム、何を作るかの判断には向かない。前提が揃わない間は、対話しながら仕様と検査方法を作る。

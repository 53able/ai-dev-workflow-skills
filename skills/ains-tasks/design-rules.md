# 方針に書く設計判断

人が design rule（境界、公開 interface、依存方向、不変条件）を先に決め、AI はその範囲で実装する。方針はその design rule を承認に載せる場所だ。

## 設計判断の5分類

方針を書く前に、この変更が次のどれを決めるかを洗い出す。

| 分類 | 決めること |
|---|---|
| component | 実行単位の分け方と、その間のやり取り（プロセス、サービス、キュー） |
| data | データの形、持ち主、内部表現を外に見せるか |
| logic | アルゴリズム、状態の遷移、どこで検証するか |
| module | コードの境界、公開 interface、依存方向 |
| naming | 型、モジュール、公開 API の名前。1つの概念に1つの名前 |

各判断に3つの問いを当てる。

- context：この判断は、今の利用者、規模、制約に合っているか
- change：どんな変更が起こりうるか。そのとき何ファイルに波及するか
- people：誰が読み、誰が保守するか。並行して作業する人やエージェントがぶつからないか

## 人が決めるものと任せるもの

基準は、戻しやすさと影響の広さ。

- 人が決めて方針に書く：module 境界、公開 API と interface の signature、データの抽象と持ち主、依存方向、層をまたぐ不変条件
- build に任せる：境界の内側の実装、private な関数の分け方、局所的な命名、テストの書き方、機械的なリファクタ

方針への書き方の例：

- `PaymentGateway` interface を `domain/payment` に置き、`infra/stripe` が実装する。domain から infra へ import しない
- 金額は `Money`（整数のセントと通貨）で渡す。境界の外に float を出さない
- `OrderService.place()` の signature は変えない。呼出し元が3か所ある

## 抽象を足す前の4条件

interface、パターン、新しい層は、次の4つがそろうときだけ計画する。

1. 明確な変更の型がある：何が、どの方向に変わるかを変更シナリオで言える
2. 安定した design rule がある：変わる部分を隠す interface が、その変更で動かない
3. 独立した進化がある：両側を別の人やタスクが別の時期に変える
4. 明示的な分離の仕組みがある：注入、設定、プラグインなど、差し替える手段が決まっている

spec、AGENTS.md、ADR に既にある規則を守るのに必要な port は、この4条件を満たさなくても正当だ。同じ tasks.md で新しく宣言した規則を、抽象を足す根拠にはしない。実装が1つの interface や「将来のため」の層は計画しない。

## 並行タスクと design rule

タスクを並行にするなら、先に design rule（タスクの間で共有する interface、型、データ形式）を決めて方針に書き、それを定義するタスクを先に置く。design rule が固まれば、それに依存する同じ層のタスクは互いを待たずに進められ、依存は「なし（並列可）」にできる。分け方と隔離は [parallel.md](parallel.md)。

## 規則を残す先

この変更を越えて続く design rule は、tasks.md に閉じ込めず AGENTS.md か ADR に戻す。戻すのは ains-retro が行う。ADR には採った理由、想定した変更、守る design rule を書く。
